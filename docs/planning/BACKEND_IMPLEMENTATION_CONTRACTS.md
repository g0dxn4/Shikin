## Reporting and classifications (complete IMP-24)

- Existing reports remain explicitly gross_cashflow by default. New net_consumption basis uses explicit allocation-level classifications; no merchant/category heuristic.
- New classification rows identify transaction_id and optional split_id, role purchase|fee|earned_income|refund|internal_inflow|cash_withdrawal|principal, optional referenced purchase-classification ID, audit timestamps. One parent classification only for an unsplit transaction; otherwise classify each existing split. Enforce uniqueness and reference consistency.
- Explicit role/type matrix for eligible ordinary posted/cleared normal-ledger rows: purchase, fee, principal, cash_withdrawal require expense; earned_income, refund, internal_inflow require income. Transfers/archived mirrors/technical kinds remain excluded and cannot be reclassified to consumption. Owning amount is the positive safe-integer transaction amount when unsplit, otherwise that split's positive amount; split_id must belong to transaction_id. Unclassified eligible allocations remain incomplete, not zero.
- Purchase/fee expense allocations contribute positive consumption; refunds negative consumption on refund posting date, attributed to the referenced purchase allocation's category. Principal, withdrawals and internal inflows contribute zero. Earned income is separate from refunds. Refund/principal MUST reference a same-currency purchase classification (not fee/refund/principal); all other roles MUST NOT have a reference. Active referenced refunds and principal are each independently capped by that target purchase's owning amount. No cycles; invalidating edits reject atomically instead of orphaning/reinterpreting relationships.
- Missing classifications/invalid or unresolved coverage return known subtotals plus explicit incomplete status/unresolved IDs, not a falsely complete average. Gross reports remain useful recorded-transaction totals with coverage disclaimer.
- Classification and split changes share audited metadata policy; reject split replacement that would invalidate existing classifications/references unless an explicit consistent remap is included atomically. No silent cascade metadata loss.

Legacy same-identity reimports compare reliable financial evidence and disclose limitations; do not fabricate a source hash. Financial mismatch conflicts, no overwrite. Explicit confirmation can bind verified legacy source identity without changing ledger fields.
- Reuse the existing canonicalStatementIdentityMaterial v1 rules without silently changing old identities: uniqueness scope is account + trimmed, case-sensitive source namespace + exact opaque external ID; fallback occurrence ordinals follow existing canonical groups and preserve multiplicity, not global content deduplication. For existing one-shot command compatibility, an omitted token means explicitly reported unreviewed_atomic mode: recompute/validate the entire plan inside the transaction, never claim it applies a prior preview. ## Reconciliation and coverage

- Implement genuine end-of-day as-of reconciliation: ordinary rows use their date; a matched transfer debit uses source date and credit uses its validated archived mirror's original posting date. Verify symmetric pair IDs, accounts, amount/currency and immutable pair shape; reject ambiguous/broken legacy pairs instead of guessing. Native unmatched transfers use their single recorded date. Compute adjustment against as-of effective ledger; update current stored balance using current ledger plus that adjustment, preserving later activity. Reject nonzero backdated adjustments that would alter any later reconciliation anchor unless the dedicated supersession workflow preserves those anchors; zero-effect observations remain possible. No future-dated observations or implied intraday precision.
- Finalize explicit posted/cleared staged selections; never promote genuine pending holds implicitly. Pending settlement is a separate explicit action. Add a separate nullable transactions.finalization_id referencing the new observation; selected ordinary rows share this ID, with a NON-UNIQUE lookup index. Do NOT overload reconciliation_id or change its existing unique bridge constraint (DELTA-01 correction). Add observation selection_mode=legacy_batch|explicit_rows, default legacy_batch for old observations, explicit_rows for new selections. Validate that member rows and observation belong to the same account and selected scope. Lifecycle guards use explicit membership for new observations; legacy ordinary effective rows retain batch protection, but a still-staged row was not finalized by the old all-rows promotion and must not be locked merely by batch name. This avoids stranding leftover pending rows after partial finalization; do not guess/backfill legacy row membership. Migration must also replace idx_reconciliations_batch_unique with uniqueness restricted to selection_mode='legacy_batch': new explicit-row observations may revisit the same batch for different selections. Keep the existing adjustment-transaction and bridge-reference uniqueness constraints unchanged. A already-finalized selected row rejects (not staged / has finalization_id), so loosening batch-level uniqueness cannot finalize it twice.
- Persist independent account/source/printed-period coverage records, including verified zero-row periods and gaps. Provisional incomplete coverage requires explicit acknowledged provenance; min/max transactions are not coverage proof.
- Bridge supersession accepts exact bridge/reconciliation + verified staged replacement IDs, retaining original rows and immutable evidence. In ONE transaction archive the original bridge (is_archived=1, retaining kind/amount/provenance/reference), activate only selected replacements, and append successor bridge/observation links. Let B be original signed bridge delta and R summed selected replacement delta effective by the original boundary: successor signed delta S=B-R, therefore R+S-B=0. If S=0 create no zero-value transaction; successor observation/correction records explicitly link null successor bridge. Original evidence is never deleted/re-written as a different amount. Selected effects must lie at/before the original boundary. Compare every later reconciliation anchor's effective value and current stored/effective balance BEFORE vs AFTER and require equality; surface pre-existing inconsistencies without claiming to repair them. Reject crossings/stale previews and roll back all changes on any failed invariant.

## Maintenance and diagnostics

- Bucket updates preserve IDs/history. Add reversal/replacement linkage columns to allocation rows; negative reversal entries reference one original positive allocation, cannot be reversed twice. Replacement/reallocation and bucket totals update atomically, currency/source caps enforced, real accounts untouched. Deactivate funded/history buckets; delete only genuinely empty/unreferenced buckets.
- Payment equation: statement.paid_amount = statement.unattributed_paid_amount + SUM(active link amounts). Add unattributed_paid_amount initialized from the existing stored paid_amount, without altering that total or account balances. Link mode apply_to_unpaid adds a link and leaves baseline unchanged (paid total increases); attribute_existing moves amount from unattributed baseline into a link (total unchanged). Unlink apply removes its amount from total, baseline unchanged; unlink attribution moves amount back to baseline, total unchanged. Recompute status from the resulting totals. New native record-card-payment operations with a real transaction create the same linked allocation atomically; statement-payment-only adds to baseline, not fake evidence. Direct explicit paidAmount edits change only baseline = requested total - active allocations and reject a negative result.
- New statement/link allocations cannot exceed statement_balance; active allocations of one canonical payment across ALL statements cannot exceed that payment's amount. Existing legacy overpaid totals are preserved and diagnosed, not clipped; no new excess allocation is permitted. Evidence must be posted/cleared, normal-ledger, nontechnical, same currency as card/statement, and either a canonical transfer into that card or an ordinary card-account income/bank-account expense explicitly confirmed by the operator as repayment to the specified card. Exclude known refund allocations and expense allocations classified as purchase/fee/cash_withdrawal from eligible repayment capacity; explicitly confirmed unclassified allocations may qualify. Cap links by this eligible capacity as well as total amount; classifications/splits that would reduce it below active links must reject until unlink/remap. Archived matched mirrors resolve only through a fully validated canonical transfer and share its cap. Unverified direction/destination requires explicit confirmation, never heuristics. Active links block financial mutation/unmatch that would invalidate evidence until explicit unlink/remap. Link/unlink creates no transaction or account-balance change; audit each baseline/allocation/status transition. Voided links must not permanently block ordinary transaction or statement deletion: retain immutable original_transaction_id/original_statement_id evidence, while nullable live foreign-key columns may become NULL on deletion only after voiding. CHECK constraints require non-null matching live references for active links. This preserves history without making explicit unlink ineffective.
- Opaque DB lineage ID + distinct local instance ID + version/schema/last-write diagnostics, never public filesystem paths. IDs initialized only at explicit initialization/migration, not report reads. Durable revision may use targeted SQLite triggers; migration must not naive-split trigger SQL on semicolons.
